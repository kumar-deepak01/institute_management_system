# Profile photo database audit

Photo bytes are stored only in the private Supabase Storage bucket named by `SUPABASE_PHOTO_BUCKET` (default `profile-photos`). Student/staff database rows contain only a server-generated object path and timestamp; no base64 or binary image data is written to a database.

| Entity | Frontend field | Endpoint | Zod / upload validation | Database columns |
| --- | --- | --- | --- | --- |
| Student | `photo` (`File`, compressed WebP, max 50 KB) | `POST /api/photos/students/:id` | `type` enum and constrained ID schema; multer 200 KB cap; allowed MIME; `file-type` byte inspection; Sharp 400×400 WebP and <=50 KB | `students.photo_path` (`text`, nullable), `students.photo_updated_at` (`timestamptz`, nullable) |
| Staff | `photo` (`File`, compressed WebP, max 50 KB) | `POST /api/photos/staff/:id` | Same pipeline and cookie, CSRF, role, and rate checks | `staff.photo_path` (`text`, nullable), `staff.photo_updated_at` (`timestamptz`, nullable) |
| Student/staff | remove photo | `DELETE /api/photos/:type/:id` | Zod params; cookie auth, CSRF, matching role, rate limit | Both metadata columns become `NULL` |

The migration source is `server/db/migrations/20261021000100_add_profile_photo_metadata.sql`; it has already been applied and must not be edited or recreated. The path is generated by the server as `students/<student_id>.webp` or `staff/<employee_id>.webp`. The bucket name comes from `SUPABASE_PHOTO_BUCKET` (default `profile-photos`) and is checked at server startup.
